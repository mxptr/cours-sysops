
# TP 6 – Pipeline CI/CD complet avec Kubernetes

## Objectifs

* Comprendre le fonctionnement d'un pipeline CI/CD complet.
* Automatiser la construction et la publication d'une image Docker.
* Créer automatiquement un cluster Kubernetes avec Kind.
* Déployer automatiquement l'application sur Kubernetes.
* Utiliser une image publiée dans GitHub Container Registry (GHCR).
* Utiliser le SHA du commit pour versionner l'image.
* Vérifier automatiquement le déploiement.
* Tester automatiquement que l'application fonctionne.

# 5. Pré-requis GHCR

Le pipeline va publier l'image Docker dans GitHub Container Registry :

```text
ghcr.io
```

Puis Kubernetes va récupérer cette image depuis GHCR.

Pour simplifier le TP, le package :

```text
cours-sysops
```

doit être accessible depuis le cluster Kind.

Dans ce TP pédagogique, utilisez un package GHCR **public**.

Cela permet à Kubernetes de récupérer l'image sans avoir besoin de configurer un `imagePullSecret`.

# 6. Créer le workflow CI/CD

Créer ou remplacer le fichier :

```text
.github/workflows/cicd.yml
```

avec le contenu suivant :

```yaml
name: CI/CD with Kind

on:
  push:
    branches:
      - main

permissions:
  contents: read
  packages: write

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    steps:

      # --------------------------------------------------
      # 1. Récupérer le code
      # --------------------------------------------------

      - name: Checkout
        uses: actions/checkout@v4


      # --------------------------------------------------
      # 2. Créer un cluster Kubernetes temporaire
      # --------------------------------------------------

      - name: Create Kind cluster
        uses: helm/kind-action@v1
        with:
          cluster_name: kind
          wait: 60s


      # --------------------------------------------------
      # 3. Vérifier le cluster Kubernetes
      # --------------------------------------------------

      - name: Verify Kind cluster
        run: |
          kind get clusters
          kubectl cluster-info
          kubectl get nodes


      # --------------------------------------------------
      # 4. Se connecter à GHCR
      # --------------------------------------------------

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}


      # --------------------------------------------------
      # 5. Construire l'image Docker
      # --------------------------------------------------

      - name: Build Docker image
        run: |
          docker build \
            -t ghcr.io/${{ github.repository_owner }}/cours-sysops:${{ github.sha }} \
            .


      # --------------------------------------------------
      # 6. Publier l'image dans GHCR
      # --------------------------------------------------

      - name: Push image to GHCR
        run: |
          docker push \
            ghcr.io/${{ github.repository_owner }}/cours-sysops:${{ github.sha }}


      # --------------------------------------------------
      # 7. Créer le namespace Kubernetes
      # --------------------------------------------------

      - name: Create namespace
        run: |
          kubectl apply -f kubernetes/namespace.yaml


      # --------------------------------------------------
      # 8. Déployer la configuration
      # --------------------------------------------------

      - name: Deploy configuration
        run: |
          kubectl apply -f kubernetes/configmap.yaml

          kubectl create secret generic cours-sysops-secret \
            --from-literal=API_KEY=demo \
            -n sysops \
            --dry-run=client \
            -o yaml | kubectl apply -f -


      # --------------------------------------------------
      # 9. Déployer l'application
      # --------------------------------------------------

      - name: Deploy application
        run: |
          kubectl apply -f kubernetes/deployment.yaml
          kubectl apply -f kubernetes/service.yaml


      # --------------------------------------------------
      # 10. Utiliser l'image publiée dans GHCR
      # --------------------------------------------------

      - name: Set image
        run: |
          kubectl set image deployment/cours-sysops \
            cours-sysops=ghcr.io/${{ github.repository_owner }}/cours-sysops:${{ github.sha }} \
            -n sysops


      # --------------------------------------------------
      # 11. Attendre le rollout
      # --------------------------------------------------

      - name: Wait for rollout
        run: |
          kubectl rollout status \
            deployment/cours-sysops \
            -n sysops \
            --timeout=120s


      # --------------------------------------------------
      # 12. Vérifier les ressources Kubernetes
      # --------------------------------------------------

      - name: Check Kubernetes resources
        run: |
          kubectl get pods -n sysops
          kubectl get deployment -n sysops
          kubectl get service -n sysops


      # --------------------------------------------------
      # 13. Vérifier les logs de l'application
      # --------------------------------------------------

      - name: Check application logs
        run: |
          kubectl logs \
            -n sysops \
            deployment/cours-sysops


      # --------------------------------------------------
      # 14. Tester l'application
      # --------------------------------------------------

      - name: Test application
        run: |
          kubectl port-forward \
            -n sysops \
            svc/cours-sysops \
            8080:80 \
            > /tmp/port-forward.log 2>&1 &

          for i in $(seq 1 30); do
            if curl -fsS http://localhost:8080; then
              echo "Application is responding"
              exit 0
            fi

            sleep 2
          done

          echo "Application test failed"

          cat /tmp/port-forward.log

          kubectl get pods -n sysops

          kubectl describe pods -n sysops

          exit 1
```

# 7. Comprendre le pipeline

Le workflow contient plusieurs étapes.

## Étape 1 – Checkout

```yaml
- name: Checkout
  uses: actions/checkout@v4
```

GitHub Actions récupère le contenu du dépôt.

```text
GitHub
   ↓
Runner
   ↓
Code source
```

---

# 8. Étape 2 – Créer Kubernetes

```yaml
- name: Create Kind cluster
  uses: helm/kind-action@v1
  with:
    cluster_name: kind
    wait: 60s
```

Un cluster Kubernetes Kind est créé directement dans le runner GitHub Actions.

Le cluster est temporaire.

```text
GitHub Runner

┌──────────────────────────────┐
│                              │
│           Kind               │
│                              │
│    Kubernetes cluster        │
│                              │
│    ┌────────────────────┐    │
│    │ cours-sysops       │    │
│    │ Pod                │    │
│    └────────────────────┘    │
│                              │
└──────────────────────────────┘
```

Le cluster sera supprimé lorsque le runner sera détruit.

# 11. Étape 4 – Construire l'image

L'image est construite avec le tag correspondant au SHA du commit :

```bash
docker build \
  -t ghcr.io/${{ github.repository_owner }}/cours-sysops:${{ github.sha }} \
  .
```

Par exemple :

```text
ghcr.io/oumar49/cours-sysops:1e3d4b0ae81628...
```

Cette image sera ensuite publiée dans GHCR.

---

# 12. Pourquoi utiliser le SHA ?

Le workflow utilise :

```text
${{ github.sha }}
```

pour identifier l'image.

Par exemple :

```text
ghcr.io/oumar49/cours-sysops:1e3d4b0ae81628...
```

Le SHA permet d'associer :

```text
Commit
  ↓
Image Docker
  ↓
Déploiement
```

Chaque exécution du pipeline produit ainsi une version identifiable.

---

L'image est publiée avec :

La chaîne devient :

```text
Code
  ↓
Docker build
  ↓
Docker image
  ↓
GHCR
```

GHCR devient le registry utilisé par le pipeline CI/CD.

# 15. Étape 7 – Déployer la configuration

Le ConfigMap est appliqué avec :

```bash
kubectl apply -f kubernetes/configmap.yaml
```

Le Secret est créé avec :

```bash
kubectl create secret generic cours-sysops-secret \
  --from-literal=API_KEY=demo \
  -n sysops \
  --dry-run=client \
  -o yaml | kubectl apply -f -
```

L'utilisation de :

```text
--dry-run=client
```

et :

```text
-o yaml | kubectl apply -f -
```

permet de rendre l'opération reproductible.

Le pipeline peut ainsi être exécuté plusieurs fois sans provoquer une erreur si le Secret existe déjà.

# 17. Étape 9 – Utiliser l'image publiée dans GHCR

Le pipeline remplace l'image du Deployment :

```bash
kubectl set image deployment/cours-sysops \
  cours-sysops=ghcr.io/${{ github.repository_owner }}/cours-sysops:${{ github.sha }} \
  -n sysops
```

Le Deployment utilise donc **l'image qui vient d'être publiée dans GHCR**.

Le flux est :

```text
Docker build
      ↓
GHCR
      ↓
Kubernetes
      ↓
Pod
```

Il n'est pas nécessaire d'utiliser :

```bash
kind load docker-image
```

L'image est récupérée directement depuis GHCR par Kubernetes.

---

# 18. Pourquoi ne pas utiliser `kind load docker-image` ?

Une autre approche aurait été de charger directement l'image locale dans Kind :

```bash
kind load docker-image ...
```

Dans ce TP, nous n'utilisons pas cette méthode.

Nous voulons représenter un scénario CI/CD plus proche d'un environnement réel :

```text
GitHub Actions
      ↓
Docker build
      ↓
GHCR
      ↓
Kubernetes
      ↓
Pod
```

GHCR joue donc réellement son rôle de registry entre la phase de construction et la phase de déploiement.

# 19. Étape 10 – Attendre le déploiement

Le pipeline utilise :

```bash

  -n sysops \
  --timeout=120s
```

Cette commande attend que le Deployment soit correctement déployé.

Si le déploiement échoue, le workflow échoue également.
