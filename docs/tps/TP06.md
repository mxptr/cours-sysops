# TP 6 – Pipeline CI/CD complet

## Objectifs

* Automatiser toute la chaîne de livraison.
* Construire et publier une image Docker.
* Créer automatiquement un cluster Kubernetes avec Kind dans GitHub Actions.
* Déployer automatiquement l'application sur Kubernetes.
* Vérifier automatiquement le fonctionnement de l'application.

## Principe

Le cluster Kubernetes utilisé dans ce TP est créé à la volée dans le runner
GitHub Actions.

Le cluster est temporaire et disparaît à la fin du job.

Le pipeline suivra le principe :

```text
Code
  ↓
Build
  ↓
Push GHCR
  ↓
Kind
  ↓
Load image
  ↓
Deploy Kubernetes
  ↓
Rollout
  ↓
Test HTTP
```

## Étapes

### 1. Préparer le workflow

Créer le fichier :

```text
.github/workflows/cicd.yml
```

Le workflow doit :

* se déclencher sur un push vers `main` ;
* récupérer le code ;
* créer un cluster Kind ;
* construire l'image Docker ;
* publier l'image sur GHCR ;
* charger l'image dans le cluster Kind ;
* créer le namespace `sysops` ;
* déployer l'application ;
* attendre le rollout ;
* tester l'application.

### 2. Versionner l'image

Utiliser le SHA du commit comme tag de l'image :

```text
ghcr.io/OWNER/cours-sysops:${{ github.sha }}
```

Une copie locale de cette image pourra être utilisée pour le cluster Kind :

```text
cours-sysops:${{ github.sha }}
```

### 3. Déployer l'application

Le workflow doit utiliser les manifestes Kubernetes du projet et mettre à jour
l'image du Deployment avec le SHA du commit.

Le cluster Kind peut charger directement l'image Docker construite dans le
runner avec :

```bash
kind load docker-image cours-sysops:${GITHUB_SHA}
```

L'objectif est de ne pas dépendre de l'accès du cluster éphémère à GHCR pour
effectuer le test de déploiement.

### 4. Déclencher le pipeline

Modifier l'application Python, puis pousser les changements :

```bash
git add .

git commit -m "Update application"

git push origin main
```

### 5. Vérifier le pipeline

Dans GitHub, ouvrir **Actions** et vérifier successivement :

* la création du cluster Kind ;
* la construction de l'image ;
* la publication sur GHCR ;
* le chargement de l'image dans Kind ;
* le déploiement Kubernetes ;
* le rollout ;
* le test HTTP.

### 6. Vérifier le déploiement Kubernetes

Le workflow doit vérifier notamment :

```bash
kubectl get nodes

kubectl get pods -n sysops

kubectl get svc -n sysops

kubectl rollout status deployment/cours-sysops -n sysops
```

### 7. Tester l'application

Le pipeline doit utiliser un `port-forward` vers le Service puis effectuer
une requête HTTP.

Le test doit valider que l'application répond correctement avant de considérer
le pipeline comme réussi.

## Résultat attendu

Un push sur `main` déclenche automatiquement :

```text
Build → Push → Kind → Deploy → Test
```

L'image est publiée sur GHCR et l'application est déployée et testée dans un
cluster Kind éphémère.

Fin des travaux pratiques : **de l'application locale au déploiement automatisé sur Kubernetes.**
